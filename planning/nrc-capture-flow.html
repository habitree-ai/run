NRC 캡쳐 중심 플로우 고도화 — 날짜 자동화와 편의 기능

2026-07-27 · 기획 검토 v1 · 대상: 집계 앱 v2 (드라이브 동기화 v2 배포 기준)

✅ 적용 현황 (2026-07-27) — P1 전체 적용: 파일명 → EXIF → 드라이브 저장일 앵커 · '오늘/어제' 앵커 보정 · 날짜 출처 힌트 · 로컬 업로드에도 동일 적용. P2 전체 적용: 2장 이상 선택 시 카드형 일괄 검토(요약 카드 · 정상 건 ✔ 저장 원클릭 · 의심 건만 ✎ 수정 · 건너뛰기 · 완료 요약) — 단건은 기존 폼 흐름 유지. P3 전체 적용: 거리×페이스≈시간 상호 검증(60초/7% 초과 시 해당 칸 강조) + 캡쳐 유형 감지(요약/상세) — 상세 캡쳐에서 구간·심박존 시계 토큰의 시간 오인 방지, NRC 헤더 절대 날짜('2026년 7월 20일' · '7월 20일' · '2026. 7. 20') 인식(연도 미표기 시 전년 보정), '오전/오후 h:mm' 시작 시각 변환, 시작 시각의 시간(duration) 오인 결함 수정. 백로그: P4 전체(BYOK 비전 OCR은 M3).

1. 배경 · 목적

이 서비스의 기본 데이터 소스는 Nike Run Club(NRC) 앱의 결과 캡쳐다. 표준 흐름은:

NRC 러닝 종료 → 결과 화면 캡쳐(폰) → 구글드라이브에 저장(자동 백업 또는 수동)
→ 앱에서 📥 캡쳐 가져오기(Picker 선택) → OCR 프리필 → 확인·수정 → 저장 → 자동 동기화

목적: 이 흐름에서 사용자 손이 가는 지점을 최소화한다. 특히 "날짜 확인·수정"을 자동화하고, 여러 장 처리 시 반복 작업을 줄인다.

2. 현재 흐름의 손이 가는 지점

단계현재손이 가는 정도
① 캡쳐 → 드라이브 저장폰의 드라이브/구글포토 자동 백업으로 자동화 가능낮음 (1회 설정)
② 새 캡쳐 선택Picker에서 직접 선택 (이미 가져온 건 자동 스킵)중간 — drive.file 스코프 구조상 선택 자체는 생략 불가(§6)
③ 날짜 확인·수정OCR의 "오늘/어제" 텍스트를 가져오는 날 기준으로 해석 — 지난 캡쳐를 나중에 가져오면 틀림 → 수동 수정 필요높음 ← 이번 기획의 핵심
④ 값 검증·저장1장씩 확인 → 저장 반복중간 (장수만큼 반복)

3. P1날짜 자동 결정 — 3단 폴백 + 앵커 보정

3.1 기준일 결정 우선순위

순위신호정확도·근거
①파일명 타임스탬프
Screenshot_20260726_081712_... 등		캡쳐한 정확한 날짜·시각. 갤럭시/안드로이드 캡쳐 파일명에 기본 포함. Picker 응답에 파일명이 포함되어 추가 API 호출 불필요. 주요 패턴: Screenshot_YYYYMMDD_HHMMSS · Screenshot_YYYY-MM-DD-HH-MM-SS · IMG_YYYYMMDD_HHMMSS
②EXIF 촬영 시각
(드라이브 imageMediaMetadata.time)		사진(JPG)엔 정확하지만 스크린샷(PNG)엔 대체로 없음 — 보조 신호. 파일 메타 조회 1회로 ③과 함께 획득
③드라이브 저장 일자
(createdTime)		당일 자동 백업이면 러닝일과 일치. 단 며칠치를 몰아서 올리면 어긋남 → 3순위. iPhone처럼 파일명에 날짜가 없는 기기의 핵심 폴백
④(최후) 빈 칸 유지신호가 전혀 없으면 현행처럼 사용자 입력 — 잘못된 자동값보다 빈 칸이 낫다

3.2 OCR "오늘/어제" 앵커 보정

NRC 캡쳐 상단의 오늘 - 8:17 / 어제 - 19:03 텍스트를 현재는 가져오는 날 기준으로 해석한다 — 잠재 오류. 개선: 위 3.1의 기준일을 앵커로 삼아 "오늘"=앵커일, "어제"=앵커일−1로 재해석한다. 캡쳐를 며칠 뒤에 가져와도 날짜가 정확해진다.

3.3 수정 가능성 · 신뢰 전달 (요구사항 "일자를 수정할 수 있게")

  • 자동값은 프리필일 뿐 — 기록 추가 폼의 날짜 필드는 저장 전 언제든 수정 가능(현행 구조 유지, 빈 칸만 채우는 원칙).
  • 출처 힌트 표시: 날짜 필드 아래 "파일명 기준 자동 입력" / "드라이브 저장일 기준(러닝일과 다를 수 있음)" 같은 한 줄 안내로 신뢰도를 전달 — 사용자가 확인할지 넘어갈지 즉시 판단 가능.
  • 시작 시각도 파일명 시각으로 프리필(러닝 직후 캡쳐가 일반적). 오차 가능성이 있으므로 동일하게 수정 가능 + 힌트 표시.
구현 규모: 파일명 파서 + 메타 조회(fields=name,createdTime,imageMediaMetadata) + 앵커 보정 + 힌트 문구 — 기존 nextDriveItem→handleFile→applyPrefill 경로에 자연스럽게 삽입되는 소규모 변경.

4. P2일괄 빠른 검토 — 반복 저장의 원버튼화

  • 여러 장 가져올 때 각 캡쳐를 요약 카드(날짜 · 거리 · 페이스 · 시간 + 썸네일)로 보여주고, 프리필이 완성된 건은 "확인 → 저장" 원버튼으로 통과.
  • 인식 실패·의심 필드(거리 없음, 페이스·시간 불일치 등)만 강조 표시해 그 항목만 손대게 한다.
  • 수정 우선 원칙은 유지 — "무조건 자동 저장"이 아니라 확인 비용을 장당 1클릭으로 압축하는 것.

5. P3NRC 인식 프리셋 강화

  • 거리·페이스·시간 상호 검증 확장: 두 값으로 나머지 하나를 계산해 OCR 값과 어긋나면 의심 표시(현행 calcConsistency의 검증 버전).
  • NRC 요약 캡쳐 vs 상세 캡쳐(케이던스·심박 격자) 유형 감지 후 유형별 파싱 규칙 적용.
  • 인식률 낮은 지표(케이던스·심박)는 M3(BYOK 비전 모델)에서 근본 개선 — §7 로드맵.

6. 제약 — 왜 "폴더 자동 감시"는 기본이 아닌가

드라이브 폴더를 통째로 감시해 새 캡쳐를 자동 반영하려면 drive.readonly(제한 등급) 스코프가 필요하다. 이를 플랫폼 공용 자격에 추가하면 Google 보안 심사 대상이 되어 "로그인만으로 연동" 전략(비민감 스코프 · 무심사 프로덕션 게시)이 깨진다. 따라서:

  • 기본(플랫폼 모드): Picker 선택은 유지하되, 선택 이후 전 과정을 자동화(P1·P2)해 체감 수고를 최소화.
  • 폴더 자동 스캔은 BYO 고급 모드 전용 옵션으로만 검토(자체 자격 사용자는 심사 무관).

7. P4중장기 아이디어

  • PWA 공유 타깃 — 폰에서 캡쳐 직후 공유 버튼 → 이 앱 선택 → 바로 OCR·저장(드라이브 경유를 건너뛰는 지름길). 저장된 기록은 기존 동기화로 전 기기 반영. manifest + service worker 필요.
  • BYOK 비전 모델 OCR(M3) — 사용자 API 키로 비전 모델 호출, 케이던스·심박 등 격자 지표 인식률 근본 개선 (drive_v1.md M3와 동일).
  • 파일명 규칙 가이드 — 사용법 문서에 "캡쳐 파일명을 유지한 채 백업하세요(이름에 날짜가 있어 자동 인식)" 안내 추가.
